## Selected flow

Keep Remote Start / PRE_SELECTION for fixed-price Vault purchases. The customer selects occupied doors on the Vault screen; the local service reserves the exact door set and persists the final tax-inclusive USD amount and immutable provider/device/request binding. It authenticates and wakes the configured Nayax terminal, then waits for a durably authenticated and exactly matched successful payment callback. Only verified payment permits the existing atomic fulfillment commit and original-door command group.

Page 36 shows Nayax/acquirer authorization and settlement before TransactionCallback. Page 47 explicitly excludes integrator Settlement from Remote Start preselection. The general statement on page 17 conflicts with that dedicated flow and resembles Device Start's separate completion rules on pages 107/123. Do not add post-door Settlement to the selected Remote Start flow. TimeoutCallback is likewise irrelevant to Remote Start preselection (page 48); it must not be treated as a no-card timeout or payment-success signal.

Retain Stripe Terminal as a separate machine-selected route. Existing sales stay pinned to their original provider, credentials' non-secret identity, terminal and transaction; switching providers cannot recreate or reconcile another provider's payment. Vault remains independent of Speedster/Card Platform V2, selling anonymous occupied doors.

## Prototype gaps addressed by this source candidate

The following findings describe the October 2 prototype and the changes selected for the October 7 core build. Present-tense descriptions in this historical findings list are not a current completeness assessment; use the follow-up scope and verification sections below.

1. Authentication profile must be explicit. PDF pages 12–13/147–150 use IntegratorId plus Signature over minified UTF-8 body + semicolon + SignKey. The current portal uses TransactionSignature over SparkTransactionId + semicolon + SignKey and adds plaintext SparkTransactionId to StartAuthentication. The existing client follows the portal. Confirm the assigned integration's contract; do not silently try multiple schemes. A document version does not prove a wire API version.
2. The receiver currently requires Amount on every TransactionCallback. Page 52 makes it conditional upon success; the valid declined example on page 59 omits it. Accept and durably ACK valid negative outcomes without inventing amounts or payment proof.
3. Post-trigger declines and terminal cancellations currently remain UNKNOWN indefinitely. Page 50 defines DeclineCallback as a terminated attempt with no authorization. Add phase-appropriate final states, reservation release and customer retry, while quarantining contradictory or late evidence and preserving completed financial facts.
4. Recovery currently forbids every outbound replay. Page 51 documents 60-second recommended timeouts and same-TriggerTransaction retries, with ten-minute GUID validity; settlement retry recommendations apply to flows that actually use Settlement. Add durable operation times, bounded retries, expiry, restart and callback-before-response handling. Confirm duplicate-presentation/current-contract guarantees before real use; never automatically create a replacement payment for an uncertain charge.
5. CancelTransaction type 2 is absent. Add a separate Admin-authorized void operation with durable intent, original identifiers, SiteId, MachineAuTime, exact amount/reason, response evidence and unresolved/manual-refund escalation. Preserve the no-automatic-refund policy and the one original-door group retry. A controller ACK does not prove physical delivery; financial compensation must not automatically restock possibly opened doors.
6. Preserve required recovery metadata. The prototype accepts approved receipts without MachineAuTime, whereas page 53 requires it and voids echo it. Confirm actual payload requirements and retain enough original evidence for compensation without unnecessary card data.
7. Certification still hardcodes Stripe in cloud certification and event validation. Add explicit Spark provider/flow/payment evidence requirements, qualified controller/machine linkage and reporting treatment for captured, voided, unknown and test transactions. Broadening a provider enum alone does not qualify a physical machine.
8. Sandbox safety is configuration-specific. The current portal says integration and production share a host; local SANDBOX flags do not prove supplied credentials cannot charge money. Require vendor-confirmed sandbox entity/device/credential bindings and acquiring payment methods, with SMC disabled. Existing software amount limits are not verified Nayax country/currency limits.

## Production protocol follow-up — October 7

The later owner-authorized production implementation extends the same selected Remote Start PRE_SELECTION acquiring protocol to explicit PRODUCTION/LIVE.
