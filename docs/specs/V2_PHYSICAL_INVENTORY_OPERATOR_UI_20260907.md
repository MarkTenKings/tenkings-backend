# Physical inventory operator workflow

This additive UI implements Mark's 2026-09-07 full-build continuation and the final operator-workflow paragraph of the financial repository's `docs/plans/2026-09-07-v2-inventory-feed-build.md`. The physical source journal and single writer are documented in `V2_PHYSICAL_INVENTORY_EVIDENCE_20260907.md`.

The new `/admin/physical-inventory` page loads one exact permanent card through a human-admin read endpoint, shows accepted custody, acquisition components and history, and guides receipt/opening, one-card physical packing, transfer/restock, completed physical sale, physical return and completed money-refund capture. It calls only the existing source writer endpoint. No generic JSON editor, database mutation path, default acquisition cost, selected FIFO rule, new Location, hardware action, payment execution, registered-customer workflow, or financial Story cost transition is introduced.

Implementation and isolated verification results are recorded below. No live data, credentials, requests, migration, service restart, deploy, commit, or push is authorized by this document.

## Implemented surface and trust boundary

- `/admin/physical-inventory` uses the existing `AppShell`, session hook and admin headers. The admin landing page links to it through the parent agent's separate navigation edit.
- `GET /api/v2/admin/inventory/card?card_id=<exact permanent ID>` accepts a human admin session. It rejects the financial read token, any `x-operator-key` header and an operator-key authority before card reads. Method and query validation, private/no-store/noindex headers and fixed error responses prevent raw database/authentication detail from reaching the browser.
- The read runs in one `RepeatableRead` transaction. It verifies canonical journal rows through the source reader, replays physical stock, checks the current card projection, and returns the complete bounded history, current components, accepted product/custody definitions and existing Locations. At most 1,000 Locations and 2 MiB of response are allowed. Oversized evidence fails visibly rather than being silently truncated.
- Existing Locations appear in a blank-start picker by name, slug and UUID. Selecting a site does not infer the external warehouse/machine ID or its binding evidence. The operator can explicitly reuse a previously accepted custody binding.
- Previously sold cards receive explicit new-acquisition guidance: physical returns and money refunds have their own forms, preserve original cost, and must not be recaptured as a new receipt. Receipt/opening requires exact card ownership, product, acquisition/invoice, lot, cycle, custody and cost evidence. Known cost is parsed with decimal-string/BigInt cent arithmetic; unknown remains null with a reason and evidence, and a documented zero remains distinct. Allocated acquisition cost is labeled as allocated and requires its supporting calculation reference.
- Packing consumes exactly the accepted loose-card stock into one distinct evidenced physical pack. Movement and sale carry the stock-origin product, component identities, acquisition cycle and costs unchanged. The screen has no cost-edit control for those actions.
- A completed physical sale requires successful-payment reference, completed-dispatch identity and their evidence, plus explicit verification of both statuses. The screen does not charge, refund, dispatch hardware, create `PackV2`, or grant account ownership. Recorded gross may remain unknown; the form asks for the evidence gap and never substitutes a product price.
- Original-sale balances derive from the verified `InventoryState` replay. Active returns and refunds are summed separately, excluding reversed adjustments. Each sale shows its source identity, returned/remaining unit count, original gross, refunded money, remaining documented money and any reason an adjustment is unavailable. Reversed sales cannot be adjusted. Unknown gross stays null; zero or exhausted gross cannot produce a positive money-refund record.
- Physical return requires blank-start selection of the exact original sale, completed physical receipt, regained house-title evidence, reason, explicit destination custody binding and source time/evidence. It restores exactly one original card or one-card pack, copying the original product definition, stock ID, pack ID, lot, acquisition cycle and component costs unchanged. No new acquisition or refund amount is generated. The UI offers only the latest unreversed sale while the card is EXTERNAL with no house stock and one unit remaining; it conservatively prevents an older acquisition cycle becoming the return basis after reacquisition/resale.
- Money refund also requires explicit original-sale selection. The operator supplies an already completed refund identity, positive exact USD amount, reason, completion evidence/time and explicit verification of completion. The amount must fit within the remaining documented original gross; no amount is selected or rounded automatically. The command carries quantity zero, no physical identities/components/custody, no new fulfilment and no ownership change. Earlier eligible sales can still receive refunds after this card has been reacquired or returned. Concurrent stale evidence remains subject to the existing serialized source writer and its conservation checks.
- Every submitted command receives an opaque browser request ID before POST. The exact command is retained in per-admin `sessionStorage` without its auth token. Double submits are blocked synchronously. Network/timeout/invalid-response uncertainty preserves that request for exact retry or accepted-history reconciliation. A receipt must match the deterministic source event ID, exact submitted financial evidence and authenticated actor before success is shown. A later failed retry cannot erase earlier uncertainty. Only an initial definitive rejection exposes return-to-draft; accepted or uncertain evidence cannot be edited in place.
- Reads are abortable and versioned so a late response cannot replace a newly selected card. Ending a write wait retains its pending record. A successful receipt stays visible even if the subsequent history refresh fails.

## Boundaries and remaining operational work

This page covers manual exact-card receipt/opening, one-card physical packing, transfer/restock, completed sale, original-card/pack physical return and completed money refund. Unpacking, reversals/corrections, historical backfill, bulk capture, raw HQ purchase receipts, generic machine/door batches and registered-customer purchase/return flows are not exposed here. Existing source history for supported backend events remains readable. An altered or opened pack requires its own supported source treatment; this page cannot substitute a loose or replacement card into an original pack return. Product and acquisition evidence are supplied by the operator, not inferred from names, valuations or payment alone. External custody bindings remain immutable; relocation needs the separately documented source treatment.

Production migration/deployment, live session acceptance, authoritative product/machine mappings, real one-machine stock-and-sales pilot and any Financial Story coverage transition remain operational work. The UTC timestamp is deliberately entered from evidence with its exact format shown. The request survives reload in the same browser tab/session; closing the browser session loses its local recovery copy, while the accepted source journal remains authoritative. No operator action was performed on real inventory.
