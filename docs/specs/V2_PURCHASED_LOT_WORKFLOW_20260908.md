## Evidence and interpretation

`inventoryWorkflowV2.ts` is the exact executable wire definition. All events carry effective/recorded time, actor, evidence and USD. Kind-specific strict payloads retain receipt, original cost choice and derived accepted unit costs, process/pack membership, reservation, asking-price history, custody moves, explicit machine/product/door loading, aggregate sales intervals, counts, removals, physical returns and money refunds. Each observation has one source event ID. Financial mapping remains explicit and separate from platform Location IDs.

A `batch_reconciled` assertion cites stored opening/closing counts, sales and movement event IDs plus separate completeness and attribution evidence. Assertions are human evidence, never independent verification. A complete assertion cannot omit another stored overlapping load, movement or sale. Nonzero opening stock and overlapping batches remain ambiguous in the financial assessor. Partial mixed-cost consumption remains unknown; no FIFO or residual sold-unit assignment exists. Refunds change money only; returns change physical quantity only and cite the original sale with independent remaining limits. An operator may identify actually returned/removed units with evidence, but unknown return/removal identities remain aggregate and unavailable for individual restocking.

The loaded unit roster remains historical membership after aggregate sales. It is never converted to a list of identified sale events. Loaded units stay unavailable for ordinary packing/transfer; only an evidenced physical removal/return can establish current possession. A new receipt never represents an unknown returned unit as a new purchase. Empty history means no evidence, not zero stock or coverage.

Historical entry may start with `opening_stock_recorded`: the evidence describes counted stock, its actual stage, one-card packs where applicable, current physical custody and the count date. A machine opening establishes an opening batch and actual nonzero opening quantity without inventing earlier HQ custody, a prior zero count or a load. It is admitted only before any accepted overlapping machine/product/door history. This origin itself satisfies the opening-count reference for a later complete reconciliation. An optional separate opening count must have the identical effective date and quantity; closing count, actual sales and scope/attribution evidence remain required. Valid later backdated evidence is accepted only if complete chronological replay still validates. Unknown purchase costs can be supplemented or corrected by a new `purchase_cost_documented` event citing the previous cost authority and source document; unit costs become unknown until an explicit complete-roster assignment supersedes the previous assignment.

The final release review planned the following bounded receipt typo recovery before code, now implemented: `purchase_cancelled.data` is exactly `{lot_id,purchase_event_id,reason}`, with the normal immutable command/event envelope. It can cancel only the cited original `purchase_received`, never a historical opening or used stock. Prior cost assignment/supplement and price documentation are harmless; any reservation, process, pack, custody, load, count or physical-sale dependency blocks cancellation, including downstream history already accepted at a later effective time. The receipt and all lot/cycle/unit IDs remain reserved permanently, while available unit holdings are removed and further cost/stock mutation on that cancelled receipt is rejected. The guided lot control records the reason; a correctly evidenced replacement is a separate new receipt with new identities. This authorized addition superseded the prior source freeze. Final source/financial integration tests and the repeated compatible production build pass as recorded below.

## Saved source and transport contract

The executable contract is [inventoryWorkflowV2.ts](../../packages/database/src/inventoryWorkflowV2.ts). `WorkflowCommandInputV2` validates `{request_id,event_kind,effective_at,evidence_ref,data}`. `recordInventoryWorkflowEventV2` supplies the accepted `WorkflowEventV2` fields `schema_version:2`, `source_event_id`, `source_sequence`, `recorded_at`, `recorded_by` and `currency:'USD'`. The event otherwise preserves the exact command. Only `cost_assigned.data.allocation` is derived: it carries method/version, residual rule, accepted complete unit costs and their basis/evidence. Neither purchase receipts nor later cost documents require a financial ledger ID, bank identity, revenue match or financial credential. The financial app owns those local links and capacity checks.

| Event | Recorded evidence |
| --- | --- |
| `purchase_received` | Stable lot/cycle and complete unit roster, actual received quantity, documented total or explicit unknown reason, acquisition document, unprocessed `hq:<id>` at an existing Location |
| `purchase_cancelled` | Original unused purchase receipt identity, lot and sourced entry-error reason; removes available holdings while permanently retaining every original lot/cycle/unit ID and evidence event |
| `opening_stock_recorded` | The same stable inventory lineage plus observed stage/product/pack roster and actual custody at the counted date; machine openings carry explicit scope and opening-batch identity |
| `purchase_cost_documented` | Current replacement total or unknown reason, new purchase evidence and exact previous cost-authority event ID; original receipt remains immutable |
| `cost_assigned` | Explicit unassigned, documented-unit, equal-card or explicit-per-card method; accepted integer-cent costs for the complete roster; exact prior assignment ID or null for the first assignment |
| `processed` / `packed` | Work state and product, optional links to actual eligible permanent cards, and one recorded card per permanent pack ID |
| `reserved` / `price_set` | Planned destination or cancellation, and independent intended selling-price history; neither moves physical stock |
| `custody_moved` / `batch_loaded` | Actual dispatch/receipt/transfer, or a uniquely named load with complete selected packed roster and exact machine/product/door scope |
| `sale_observed` / `stock_counted` | Completed, nonoverlapping sales interval with quantity and actual revenue or unknown, or a counted quantity with explicitly identified remaining roster only where observed |
| `batch_removed` / `physical_return_observed` | Quantity and actual destination, original batch, and optional evidence-identified unit roster; returns cite the original sales observation and have an independent cumulative quantity limit |
| `refund_observed` | Unique refund reference, original sales observation, and completed amount bounded by its remaining documented gross; no stock effect |
| `batch_reconciled` | Actual opening/closing, sales and other movement observation IDs; independent completeness/attribution assertions and evidence; exact superseded assertion ID |

`GET /api/integrations/financial/inventory-workflow-events` accepts `after_sequence`, `limit` (1–1,000) and an optional pinned `snapshot_through_sequence`. It returns `WorkflowExportV2`:

```ts
{
  page: {
    schema_version: 2,
    source_system: 'ten-kings-card-platform-v2',
    snapshot_id: 'v2-inventory-workflow:<boundary>',
    after_sequence: number,
    through_sequence: number,
    events: WorkflowEventV2[]
  },
  snapshot_through_sequence: number
}
```

This is the same source authority as the existing exact-card feed so one source-to-financial machine mapping can apply to both. It has a separate journal, endpoint and financial cursor table. Sequence zero means no accepted evidence; there is no shared ordering with schema v1. Every page is contiguous, validated against the fixed high-water boundary, and verified against stored canonical hashes and actor/request binding. Export queries fetch a cumulative byte-budgeted chunk, not one SQL query per event. History replay uses those pages without an arbitrary lifetime event/byte ceiling. The HTTP response is capped at 10 MiB, commands at 1 MiB and saved canonical command+event at 2 MiB; a single intake or load has at most 2,000 units. These are request bounds. Full replay cost still grows with accepted history and has not been benchmarked at production lifetime volume.

The existing `FINANCIAL_INVENTORY_READ_TOKEN_SHA256` capability grants only this and the exact export. Human-admin `GET` and `POST /api/v2/admin/inventory/workflow` use the existing authenticated admin session. POST takes `{mode:'preview'|'record',command}`; preview and save enter the same locked validator. Static operator keys and the financial bearer are rejected before any admin data read or write. All responses disable caching; authentication/infrastructure errors do not expose secrets or database detail.

## Writer, custody and commercial availability

Only [cardPlatformV2.ts](../../packages/database/src/cardPlatformV2.ts) appends accepted workflow evidence. It takes the exact-card advisory lock before the workflow lock, reads verified history, allocates cost at the command's effective time, validates the complete resulting chronological history and appends `MAX(sequence)+1` in one READ COMMITTED transaction. Rollback consumes no sequence. An exact retry from the original actor returns the original event even after later history; changed input or actor conflicts. PostgreSQL enforces immutable rows/truncation denial, sequence order, canonical content hash and envelope binding. The writer verifies the stored row before returning success. Read views use repeatable-read snapshots.

Custody identities have immutable Location bindings across both journals. HQ/machine custody requires the existing physical Location; named transit can have no Location. No machine is inferred from a Location name or shared address. Raw workflow stock never dual-writes V1 or the existing exact inventory journal.

An optional permanent-card processing link locks the existing card and requires HOUSE ownership, null `currentOwnerId`, and GRADED/IN_INVENTORY state. An active exact-card journal, listing/pack assignment, account ownership or shipping state makes it ineligible. The reviewed workflow migration adds `CollectibleCardV2_workflow_custody`: linked cards cannot separately change lifecycle, owner, physical Location or sale mode, or be deleted. This blocks ordinary commerce and `voidCard` from claiming an identified sale or different physical stock authority. Unrelated grade/identity/comps/NFC fields can retain their existing authorized workflows. This checkout does not yet implement the broader PackV2/ShipmentV2 commercial engine; it must continue honoring this database guard when implemented. There is no implicit release of a linked card into exact commerce after aggregate sales, and no guessed linkage between a vend and that card.

## Operator path

Open **Admin → Physical inventory → Purchased lots and batches** using the existing admin session. The exact permanent-card workspace remains available in its own tab.

1. Choose **Receive purchased lot**, record the acquisition evidence, actual quantity and HQ custody, and explicitly confirm the complete roster. Leave cost blank with a reason if undocumented. The generated IDs identify that received bookkeeping roster; no graded-card rows are created.
2. For a quantity/lot/roster entry typo, select the original purchase and **Cancel unused receipt entry**. The control shows its exact original quantity and eligibility, requires the reason and explicit acknowledgement, and uses the same causal preview/save path. It preserves the receipt and removes its available holdings. A replacement is a separate new receipt with new identities. Historical openings and any reservation/physical use are ineligible.
3. Select the purchase. Download its complete roster when using documented individual amounts or an explicit per-card allocation. **Assign acquisition cost** begins with no selected policy. Known assignments must cover the entire received roster and conserve the current total exactly, even if only some units are processed. **Document / correct purchase cost** adds new source evidence and clears current per-unit cost until a fresh explicit assignment is saved.
4. Select the actual units for processing, record their product, finish processing, and save one-card pack membership. Optional permanent-card links must identify real eligible cards. Asking price and planned reservation are independent controls.
5. Record actual dispatch into named staff/vehicle transit custody, then **Load machine batch** when packed units reach the actual machine/product/door. Machine loading is distinct from a reservation and from receipt at HQ.
6. Save actual sales observations and opening/closing stock counts. Select **Reconcile batch evidence**, cite stored observations and any other overlapping loads/removals/returns, and record completeness/attribution evidence only when known. The financial assessor evaluates the evidence; an operator assertion alone does not prove cost coverage. Missing and partially identified stock remains uncertain.
7. Record actual removal or physical return separately from completed money refund. A return references its original sale. Select individual units only if the physical evidence identifies them. Monetary refund history appears with the original related batch/lot observation, despite having no stock or unit fields.

For historical reconstruction, use **Record historical opening stock** with the actual counted date, custody, observed stage and recorded one-card packs. A machine opening needs no invented earlier HQ event or zero count. Later complete reconciliation can leave **Opening count event ID** blank because this opening is already the source count. Enter other historical steps through the ordinary forms with a sourced effective UTC date; **Preview causal impact** validates all later accepted history before save. No prior business event is invented merely to make a timeline balance.

The UI pages lot, batch and evidence lists in groups of 100 and returns only the selected roster (at most 2,000 units); the roster table pages 100 rows. Per-admin same-tab session storage preserves the exact unresolved command across reload; no token is stored. It verifies the accepted receipt's request hash identity, actor, kind and submitted evidence before clearing a retry. Lost/mismatched responses preserve uncertainty and freeze that command for exact retry. A session/admin change resets pending view state; delayed reads and writes cannot replace the new session. Synchronous navigation guards prevent an in-flight save from racing a view change. Closing the browser tab removes that tab's recovery storage, so reconcile an unresolved save with the authoritative journal before creating a different request.
