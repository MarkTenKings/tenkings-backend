## Implemented source boundary

- `packages/database/src/cardPlatformV2.ts` owns `recordCardInventoryEventV2(tx, input, authenticatedAdminId)`. Call it only in one READ COMMITTED transaction. Its transaction-scoped advisory lock serializes global source sequence assignment. Canonical request hashing makes retries exact and leaves later card state unchanged. The immutable journal, permanent-card projection, and any ownership event commit together. The writer checks its deferred database projection constraint before returning success.
- `cardInventoryV2.ts` defines the strict financial schema-v1 contract and stricter one-card operator command; `cardInventoryV2State.ts` performs deterministic stock replay. Every component names the permanent card, acquisition lot/cycle/document, and known integer cents or an explicit unknown reason. The producer does not allocate, estimate, or turn selling/market prices into cost.
- `cardInventoryV2Read.ts` verifies canonical content/request hashes, event identity/sequence/clock, strict payload schema, and source coverage before exporting. Card replay is bounded to 10,000 events and 10 MiB; exceeding it fails explicitly. Export pages remain below 10 MiB, including multibyte evidence, by reducing emitted event count and resuming contiguously.
- The Prisma model declares `CardInventoryEventV2` and its permanent-card relation. The reviewed migration is `packages/database/prisma/migrations/20260907190000_card_inventory_events_v2/migration.sql`; its bytes exactly match the retained `packages/database/schema-proposals/20260907_card_inventory_events_v2.sql`. Its content-hash checks, append-only UPDATE/DELETE/TRUNCATE guards, transaction-serialized sequence, projection guards, and JSON expression indexes accompany activation; Prisma cannot represent all those constraints. The card FK uses `ON DELETE RESTRICT` and `ON UPDATE NO ACTION`; recording time is `timestamptz(3)`. The historical INACTIVE header remains unchanged solely to preserve the reviewed SQL checksum; publication state comes from the actual migration directory and recorded release evidence.

## Operator and financial APIs

`POST /api/v2/admin/inventory/events` uses the existing ordinary human-admin bearer session. It does not accept the static operator key or financial read capability. The body is exactly `CardInventoryCommandV2Input`:

- `request_id`, `card_id`, `product_identity_ref`, `custody_bindings`, `ownership_evidence_ref`, `fulfilment`, and `event` are required; unknown fields are refused. Request size is at most 64 KiB.
- `event` supplies every financial event field except `source_event_id`, `source_sequence`, `recorded_at`, and `recorded_by`. Those are server-owned. Opening, receipt, and packing commands set `stock_id=null`; the resulting stock ID is the new server-assigned source event ID. Other operations cite the original stock ID and preserve its exact acquisition components.
- A loose opening/receipt has `unit_or_pack_id=card_id`. A pack has one separately evidenced physical pack ID, one input stock with quantity one, and exactly that permanent card's captured components. Pack identity is never reused and cannot impersonate a permanent card ID. This is a physical-evidence assignment, not a `PackV2` commerce engine or physical QR scheme.
- Each from/to custody has exactly one binding containing `custody_id`, an existing `location_id` UUID, and `evidence_ref`. A `machine:<external-device-id>` is distinct from Location identity: multiple devices may share a site. Multiple products/batches may share a device. The product identity reference and custody-to-Location binding are immutable; device relocation requires a reconciled identity cutover or later relocation extension.
- A manual physical sale requires `fulfilment.payment_status=SUCCEEDED`, its payment reference, `physical_status=DISPATCHED`, its exact dispatch reference matching `external_sale_id`, and the source evidence reference. Gross cents may be unknown. No API call collects payment, operates a machine, claims an automatic fulfilment, or independently authenticates an external document.
- Opening, acquisition, return, and reversal require explicit house-title/correction evidence. Returned title is recorded as `ADMIN_CORRECTION`, not a fabricated TKD buyback. Account-owned, vaulted, shipping, direct-listed, and void cards are excluded. Refund is money only; no loss/shrinkage/stock-void event is implemented. Once tracked, a card's lifecycle cannot be changed outside the journal; existing `voidCard` therefore refuses tracked inventory cards, while untracked grading/card behavior remains intact.

`GET /api/integrations/financial/inventory-events` uses a separate server-only `FINANCIAL_INVENTORY_READ_TOKEN_SHA256` credential. Store the lowercase SHA-256 of a separately generated 32–512 character visible-ASCII bearer token; do not reuse an admin session or put either credential in browser configuration, URLs, or logs. The endpoint grants read export only and checks the token using timing-safe comparison before database access.

Query parameters are `after_sequence` (required), `limit` (1–1,000, default 1,000), and optional `snapshot_through_sequence`. The first page fixes the committed maximum; subsequent requests repeat that bound. The strict response is `{page, snapshot_through_sequence}`, with `page.source_system=ten-kings-card-platform-v2`, `page.snapshot_id=v2-inventory:<bound>`, and consecutive events after the requested cursor. Unknown/future bounds, gaps, malformed data, or altered hashes fail closed. Empty pages are allowed only at the bound. Every response disables caching and contains no secret or raw SQL error. The financial app pulls outbound; this source receives no financial-app credential or webhook.

The human capture/read interface has separate implementation notes in [the operator UI specification](V2_PHYSICAL_INVENTORY_OPERATOR_UI_20260907.md). That agent owns final UI validation; backend evidence below does not certify a browser workflow or a real operator pilot.
