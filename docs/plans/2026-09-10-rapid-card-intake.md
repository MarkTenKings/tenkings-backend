# Rapid individual card intake — September 10, 2026

Mark requests a default individual-card flow: sign in, Add inventory, front/back camera captures, OCR plus specifically GPT-6 Astra filling descriptive card fields, phone location filling the known inventory location/type, manual cost and expected sale price, then confirmed save followed immediately by the next card camera. Current stock/new purchase are both owned stock and should not dominate entry; historical sold-through inventory is a separate evidence workflow. Remove the initial processing-condition selector.

1. Keep ordinary entry one card by default. Move optional receipt provenance/date/notes into More details; default to an on-hand inventory entry without inventing a new purchase or sale. Retain batch/manual entry and the existing journal semantics. No processing or packing is inferred from images/GPS; newly cataloged cards start with no processing record.
2. A scoped continuous rear-camera component captures front/back with previews, retake and library/HEIC alternatives. It retains session camera access between confirmed saves, stops tracks when the modal closes, and never depends on programmatically reopening a native picker after an async save. Return to the next card only after matching RECORDED/REPLAY acknowledgment; uncertain saves keep exact request identity and photos.
3. On first capture, request browser geolocation and compare only existing authenticated Location coordinates (including current address lookup). Accept a unique nearby point within bounded accuracy; preserve manual corrections. Reuse location within the entry session and refresh stale fixes. Known inventory types may fill automatically; venue taxonomies such as mall/arena do not prove custody type or that a card was loaded into a machine. Missing or ambiguous identity/type remains a simple choice rather than an invented assignment. Exact phone coordinates stay in memory only.
4. Reuse Google OCR and OpenAI server foundations for an authenticated, bounded, no-write identification endpoint. Input is exactly the verified private front/back photo keys; fetch bytes through storage, never arbitrary caller URLs. GPT-6 Astra, low reasoning for latency, strict nullable JSON fields and photo/OCR evidence produce editable suggestions only. Treat OCR/images/model output as untrusted; never estimate acquisition cost, selling price, location, grade, authenticity or ownership. No provider/model substitution. Failed/unavailable AI leaves manual entry and photos available.
5. Extend the existing item_described JSON metadata with optional back_photo_key and optional typed card_details (manufacturer/card_number/year/set_name/variant/card_type). Keep missing keys absent for historical event hashes. Verify/sign both photos for staff, preserve both across edits, and keep private keys out of the financial operational snapshot. Update the financial journal parser before source can emit the new description keys. No SQL migration, direct database writer or grading identity is introduced.

Use temporary fixtures only. Review against the governing principles and blueprint before commits. Preserve unrelated ATLAS releases and existing collect branch lineage.
7. If consumer code changes are necessary, protect the local financial service with its existing verified-backup/restart process and confirm current sync first.
