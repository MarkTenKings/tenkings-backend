## Shared interfaces

The staff API adds `workspace` operations beneath its existing authenticated `/api/staff` boundary (externally mounted beneath `/admin`). All mutations use an `operationId` retained across uncertain replies and an `expectedRevision` where a saved card exists. Authority is derived from the current staff session. The browser never selects a source owner, internal authorization hash, provider configuration or grading formula.

- `GET workspace`: `{ cards, readiness }`. Each card has `id`, `title`, `subtitle`, `revision`, `state`, `stage`, `sides`, `operator`, `specimenId`, `updatedAt`, and an optional safe `attention` message. States are `DRAFT`, `WAITING`, `IN_PROGRESS`, `NEEDS_ATTENTION`, `HUMAN_REVIEW`, `APPROVED`. Stages are `PHOTOS`, `IDENTITY`, `PREPARATION`, `CENTERING`, `INSPECTION`, `REPORT`, `REVIEW`, `FINISHING`.
- `POST workspace/cards`: `{ operationId, title, identity }`, returns `{ card }`. Identity is bounded category-aware human input, not inferred from filenames. Creates one recoverable physical-card draft; multiple drafts may be prepared independently. Explicit Front/Back pairing remains a human action.
- `GET workspace/cards/:id`: `{ card }`, including safe saved workspace data and links into the existing exact report/correction surface when `specimenId` exists.
- `POST workspace/cards/:id/upload-plan`: `{ operationId, expectedRevision, side, file: { name, contentType, byteCount, sha256 } }`, returns `{ card, upload }`. A direct-storage upload grant is a narrowly scoped transient transport, never an evidence identity or a persisted URL. No image body traverses Vercel JSON.
- `POST workspace/cards/:id/upload-complete`: `{ operationId, expectedRevision, uploadId }`, returns `{ card }`. Only server-verified exact object bytes may mark a side verified. Replacing a side produces a new capture binding and never edits prior evidence.
- `POST workspace/cards/:id/queue`: `{ operationId, expectedRevision, pairConfirmed: true }`, returns `{ card }`. Both verified photographs are required. Upload/queue population dispatches no paid work. Up to ten fresh-photo cards may wait before processing begins.
- `POST workspace/cards/:id/claim`: `{ operationId, expectedRevision, operator: 'HUMAN' | 'ASTRA', mode?: 'CONTINUOUS' | 'STEP' }`, returns `{ card }`. Claims are exclusive and fenced against exact capture and workflow revisions; active/unknown work never silently expires into a fresh paid attempt.
- `POST workspace/cards/:id/action`: `{ operationId, expectedRevision, action, payload }`, returns `{ card }`. Concrete manual actions and their payloads are confirmed by the lead/private grading adapter; reuse original geometry, centering, inspection and deterministic grading logic. The UI cannot manufacture completion or grade values.
- `GET workspace/cards/:id/activity`: `{ activity, control }`, a bounded safe projection of recorded actions/proposals/effects. Never return raw model continuations or provider requests/responses.
- `POST workspace/cards/:id/control`: `{ operationId, expectedRevision, action: 'PAUSE' | 'RESUME' | 'STEP' | 'TAKE_OVER' }`, returns `{ card, control }`. Pause stops new dispatch; pending work remains visible and held. Takeover commits only at a settled boundary and fences late results. Final human approval remains the existing exact-report operation.

Errors use the existing safe HTTP error protocol. No unauthenticated or customer route gains access. Saved workflow metadata references the one authoritative source/evidence and existing specimen/revision/assignment/run records; it does not create a competing grade or copied historical session. Readiness is explicit and must distinguish photo storage, preparation, manual grading and Astra runtime availability.

## Integrated execution contract

The staff claim/Resume/STEP handlers first commit the durable operation, then resolve its immutable database operation ID under the authenticated actor. They send exactly `{ runId, commandId }` through the existing signed workspace transport as `EXECUTE_ASTRA`; neither value supplies authority or provider configuration. A private acknowledgment follows read-only admission against the saved command, current controls and original claimant. It does not itself reserve cost or grant execution. The private host runs at most one physical card at a time and only coalesces the same command ID and canonical command hash. A newer STEP remains retryable while its predecessor drains. A settled acknowledgment requires durable evidence that the exact command was consumed, paused or superseded, so a lost reply cannot execute the step again. Unknown or orphaned in-flight work remains held. Uncertain HTTP replies retain the original operation for same-ID recovery.

The private service has separate SOURCE and COORDINATOR clients. Each transaction checks the actual role's effective privileges. The independently verified operator artifact owns its separate OPERATOR client and fixed provider configuration; its existing CLI and version2 release manifest remain unchanged. The finite dispatcher coordinates original-photo review, Front/Back preparation and report initialization, then the linked report review. Source commands are checked inside the transaction before creating a fresh reservation or action. Operator execution carries the expected control revision into the original locked claim transaction, closing the gap between dispatch admission and native artifact startup. Pause, STEP, takeover, expired authority and unresolved outcomes are rechecked at durable execution boundaries; receipt recovery preserves its original authority and cost hold. Service shutdown stops admission and aborts active execution without clearing retained records or cost holds.
