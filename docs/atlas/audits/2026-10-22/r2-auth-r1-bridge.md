# R2 inert R1 authentication bridge

October 22, 2026. Source-only work in the R2 marketplace worktree. No R1 file, cookie, router, schema, deployment or credential was changed. The bridge defaults off; it does not grant title, Fingerprint eligibility, marketplace policy approval or staff marketplace privileges.

`src/auth-r1.mjs` exports `createR1MarketplaceAuthBridge`, `R1_SESSION_ACCESS_ACTION` and `R1_SESSION_ACCESS_SCHEMA`. Trusted composition supplies the actual R1 canonical classes and existing state: `staff: {state, boundary, DurableStaffAuth}` and `customer: {state, CustomerAuth, CustomerDatabase}`. Explicit approved policy contains `approvalRef`, marketplace `environment`, R1 `r1Mode`, allowed `staffRoles` and allowed `customerRoles`. REVIEWER is not automatically a marketplace grant. An independent server `admitRequest` limiter is mandatory because R1 ingress admission verifies route proof, not marketplace rate budgets.

`bridge.open(originalRequest, {audience})` yields request-scoped `resolveSession`, `issueCsrf`, `verifyCsrf`, `admitRequest`, `withAuthorized(principal, async actor => dispatch(actor))` and `close`. Audience is chosen by trusted server composition, never body or cookie claims. The exact original request is admitted once through the existing synchronous R1 guard and pinned across every asynchronous step. Prototype methods, runtime/config references and approved policy are pinned. Private, frozen principals cannot be recreated by spreading their public fields. `close` or the bounded request deadline ends the capability. Marketplace-purpose CSRF uses the existing canonical auth digest over bound session/browser hashes, audience and policy reference; no cookie decoder identifies an account and no new session is issued.

Staff authentication retains the exact WeakMap-backed handle returned by `DurableStaffAuth.authenticate`. `withStaff` reads the live identity/session; the existing manual boundary's `transaction(originalHandle, callback)` revalidates through `atlas_manual.authenticate` in separate short transactions immediately before and after dispatch. The service/provider work runs only after the first authority transaction closes and before the second opens: no Stripe wait holds R1 authority row locks or its five-second Prisma transaction. Fresh role/access-version checks use the same original opaque handle, which is never serialized into the marketplace actor. This STAFF surface can write, so OBSERVER is rejected even if an explicit policy includes it; only an explicitly approved REVIEWER mapping is supported. Post-work revocation suppresses the response without asserting rollback of an already-committed effect. The separate bounded request deadline still applies.

Customer identity is read only through the actual `CustomerDatabase.prototype.call` using fixed action `marketplace_session_access` and the two hashes from canonical `CustomerAuth.authority`. The exact result is `{schema:'atlas-marketplace-session-access-v1', accountId, sessionHash, browserHash, expiresAt, observedAt}`; times are integer epoch milliseconds, hashes must match, and unknown fields, stale results and changed accounts are rejected. Current R1 has no passive identity action with this contract. Missing action therefore remains unavailable. Existing bootstrap is deliberately not repurposed: it can create/rotate browser state. Customer live access is rechecked before and after dispatch. A revocation or transport failure after a separately committed effect suppresses the response but is not rollback evidence and must not trigger an automatic retry.

`sql/r1-session-access-proposal.sql` is an inert proposed R1 gateway wrapper with an unconditional exception guard. It remains outside migration manifests and has not been applied to shared R1. Its proposal preserves the single EXECUTE-only `customer_call` entry point and existing action delegation, validates exact deployment binding and hash-only input, locks current account/session/browser/control state, rechecks expiry after locks and returns no phone/profile fields. All object references are qualified and the function search path is only `pg_catalog`. It proposes no table grants, role creation, session extension, bootstrap, claim or marketplace activation. R1 must review the actual deployed wrapper chain, owner/ACLs, privilege qualification and release binding before adopting a separate migration and deliberately removing the guard.

The separate `test/r1-session-proposal.integration.mjs` qualification passed against the exact canonical R1 standalone baseline in an owned PostgreSQL 17 cluster. The original guard first refused; only the explicitly recorded in-memory test copy removed it. Actual canonical CustomerDatabase/CustomerAuth, exact closed response/binding, prior action delegation, one executable gateway, old-wrapper/direct-table refusal, expiry/revocation/access-version checks and no-write snapshots passed. All pools closed and the cluster stopped. The earlier fixture seed refusal is retained separately; its retry followed the canonical LOCAL_FIXTURE exemption without changing a trigger or sending SMS. Full source hashes, receipts, limits and deployment distinctions are in [the host integration audit](r2-host-integration.md).

An explicit `maxDatabaseClockSkewMs` option defaults to zero and cannot exceed 2000 ms. Freshness includes the allowed lead conservatively; session expiry subtracts that lead. Arbitrary future observations, stale results, clock rollback and expired request deadlines refuse authority. A real owned database observed 500 ms ahead of the test host clock passed with an explicit 1000 ms tolerance and failed with zero tolerance. This never extends a session or changes its stored timestamps.

Concrete deployment binding still required: R1 customer cookies use `Path=/account`; staff cookies use `Path=/admin`, and the site router signs those zones. Root must mount the corresponding marketplace surfaces/APIs within their existing zones and pass the unmodified original request to admission. This bridge neither broadens cookies nor rewrites signed ingress paths. Actual R1 constructors/state, the restricted customer gateway action, approved staff marketplace role policy and request limiter must be supplied by reviewed composition.
