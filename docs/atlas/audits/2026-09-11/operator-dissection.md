**There is also an imminent independent size limit.** Current `inputCanonical=12,207,165` bytes leaves only **375,747 bytes (366.9 KiB; 2.99%)** below 12 MiB before adding the next request envelope. ## Minimal desired architecture and completion criteria

A compact run header should contain card ID, actor/claim fence, state/control, revision, deadline, current action and lease. An immutable request artifact contains the bounded provider input and image manifest. An attempt row holds request hash/key, dispatch token, provider state and receipt key. One durable receipt leads to one validated action result and one atomic revision advance. The rendered workspace and both human/machine controls use those same action transitions. The deterministic source/grading/report kernel remains underneath them.

The simple flow is:

`verified photo pair → one preparation proposal → deterministic validation/prepare → immutable initial report → bounded inspection/correction actions → human final review`.

Each action is independently resumable from its saved receipt or worker result. UI reads use a compact projection. A transient DB interruption with no unresolved external action becomes suspended with Resume and Take Over available. An actual unknown paid outcome remains explicitly held. Image artifacts are stored once; request context is selected and bounded before payment; lease renewals never inspect or rewrite them.

Deliver the work in three reviewable increments:

1. **Recoverability and diagnostics:** fix the settled FAILED/control-running dead end, add exact phase/query/lock/byte timings, and verify saved-response replay does not make another provider call. Any recovery of this specific live run needs a deliberate durable transition preserving current evidence, accounting and owner constraints; no blind table edits were performed in this audit.
2. **Persistence simplification:** split large immutable payloads from hot run/attempt metadata, make lease/receipt paths small, remove per-transaction ACL inventories and global locking from ordinary reads, and reduce per-card lock scope. Migrate guard invariants together, rather than bypassing SQL checks from JavaScript.
3. **Fewer model/worker round trips and shared actions:** combine identity plus both boundaries into a validated coarse proposal; prepare sides concurrently when the underlying worker permits it; make machine inspection corrections use the same real action/recompute path as human corrections; bound image context explicitly.

Meaningful acceptance cases: fail reservation before dispatch and successfully resume or take over; receive a paid response then fail application and apply it exactly once on recovery; late receipt after takeover cannot overwrite human work; duplicate dispatch token is rejected; wrong-card/old-revision evidence is rejected; original hashes and immutable report history remain intact; context cannot grow without a preflight route; heartbeat/receipt latency remains bounded as audit history and photo sizes grow. Run them against disposable PostgreSQL with current constraints, not mocks that repeat the implementation.
