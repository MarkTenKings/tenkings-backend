# ATLAS standalone database: source and cutover map

Date: 2026-10-13. Planning evidence only; no deployment, production query, database creation, role change, or deletion was performed for this map.

## Decision and scope

Use a dedicated ATLAS PostgreSQL cluster and a dedicated database, with separate least-privilege ATLAS roles. Keep the current monorepo and build only the current ATLAS serving dependency closure. A second logical database on the Ten Kings cluster removes ordinary cross-database SQL access but still shares the cluster administrator, resource limits, backup lifecycle, and failure domain; it does not meet the requested complete operational separation.

Do not clone the shared database, replay all public migrations, or import physical-card/lesson history. Bootstrap a reviewed standalone schema from the current R15 object definitions, remove legacy staff dependencies, and import an explicit small retained-data allowlist. Retire old ATLAS access after validating the replacement. Deleting or relocating the Ten Kings cluster is a separate Ten Kings operation, not implied by ATLAS cutover.

This plan uses deployed source `8dc73ae21c64c2f12a80e4b804a186fe41b1cfc8` and current source `329946763c3a79872eaee43db415cedd7ca42f1f`. Later local planner/test/documentation changes are not the deployed R15 source.

Change `lib/server/http.mjs:22–49` and the legacy handlers below to remove old cards/workspace/evidence/identity-correction/learning/operator API branches. Preserve current connected-manual proxy and auth routes. Remove obsolete old card/workspace/operations pages from the packaged current app as the implementation audit confirms their role; update `scripts/check-boundary.mjs:10` and tests to enforce the resulting exact current route set. Do not remove current manual finishing, current customer order desk or current dealer functionality because of similar names.

## Clean standalone schema extraction method

1. Freeze a candidate source and define the actual current route/worker/role set. Implement the current-only staff contract above first. Pin every SQL function/table/type/index/constraint/trigger and the generated-client schemas needed by that contract and by the current manual/customer/commerce/dealer gateways.
2. Under a separately authorized read-only export, capture a consistent **schema-only** custom-format dump of the seven ATLAS schemas, with no data, ownership or ACL restoration. Use a parsed `pg_restore --list` object manifest and an explicit reviewed include list, not regex deletion of SQL. Reconcile live definitions/checksums with the committed migration sources. The retained R15 schema receipts supply the starting identity, not a complete fresh dump.
3. Compute dependency closure through `pg_depend`, function signatures/composite types, triggers, views and function bodies. PL/pgSQL/dynamic SQL needs source inspection too. Exclude every legacy public AiGrader dependency and old-version object. Include the current immutable/deferred triggers, security-definer search paths, crypto/UUID primitives and correct owner semantics. Do not bring back an empty public AiGrader compatibility table just to make a legacy function compile. No FDW, dblink, foreign server or old-host SQL bridge is permitted.
4. Write a new explicit standalone baseline migration and dedicated migration lineage. Restore that baseline from empty on disposable PostgreSQL 17, then replay the new migration runner and require a no-op. Retain the old 86/121 ledger hashes as lineage evidence; do not claim the historical shared migrations executed on the new database and do not copy the public121 ledger. Keep existing generated clients where their schemas remain correct; Prisma model-only schema push is insufficient because most current behavior is raw SQL, gateways, grants and triggers.
5. Provision a non-serving schema owner/migrator and new staff, manual, variant, customer web and customer private roles. Apply the current exact runtime grants, revoke broad PUBLIC CREATE/EXECUTE as appropriate, and run each actual role's privilege checker. Serving roles cannot promote lessons. The owner-directed local cleanup removes the old offline activation CLI; do not copy it into the standalone artifact. Any future activation mechanism requires its own separately reviewed implementation and Mark approval for the exact evaluated release.
6. Import the reviewed data manifest in dependency order while controls/admissions and workers are fenced. Use exact row hashes, immutable receipt bytes, FK checks and trigger-aware import procedures. Recreate fresh control bindings for the new candidate deployment, enable only after qualification, and keep learning on the empty neutral release.

This is a bounded installer and legacy-boundary change around current R15, not a rewrite of grading, commerce, photo processing or customer flows. The exact reduced relation count is deliberately not guessed; it is an output of steps 1–3.
