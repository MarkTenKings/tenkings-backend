## Proposed shared boundary

| Shared capability/data | Company-specific records/actions |
| --- | --- |
| Image/OCR interpretation, normalized card fields, taxonomy and parallel candidates | Photo ownership/access and the physical card instance |
| Corrected aliases, identifying marks and reusable reference examples | Inventory quantities, location, acquisition cost, owner and customer |
| SoldComps transport, matching logic and timestamped eBay evidence | Each company's comp selections, adopted valuation and financial postings |
| One maintained implementation and compatible field contract | Grading stage, report, approval, listing, sale and fulfilment |

Start with a shared server-side package for the reusable request/parsing/lookup functions, rather than two copied implementations. Both application adapters can call the same functions without requiring a new network service merely to share code. A narrow common catalog/feedback store supplies relevant knowledge to both. A separately hosted engine can be considered if deployment topology warrants it; it is not a prerequisite. Credentials remain server-side. Sharing existing provider resources does not require a shared inventory or a system-wide execution lock.

An inventory item means a physical copy owned/held by a company; a catalog identity means the card design and variant. Those must remain distinct. A confirmed correction to a variant name can help both companies; a particular copy's serial number, damage, location or purchase price must not become a universal fact about that design.

Human corrections already deliberately supplied in either app can be the validation event for publishing reusable identity knowledge. Preserve their source/context/version without adding a second approval workflow. Model guesses stay distinguishable from confirmed corrections. Sharing identity knowledge does not automatically authorize mixing all grading lessons or financial information.

## Detector technology recommendation to evaluate

Keep SAM 3 as the current mask/measurement baseline. Test an Astra-led candidate finder/classifier feeding precise regions into SAM, with the existing deterministic measurement and grading math. Compare it with the current heuristic-first detector using the same photographs and human-reviewed expected findings. Do not assert that adding Astra is faster or more accurate before that comparison.

| Job | Proposed tool responsibility |
| --- | --- |
| Read identity and distinguish variants | Existing Ten Kings Google Vision + Astra/reference engine |
| Find suspected damage and interpret defect type | Evaluate Astra visual reasoning with relevant corrected examples |
| Trace exact affected pixels | SAM 3 and existing precise editing/mask tools |
| Calculate area, centering and grade | Existing deterministic engine |
| Draft reusable card maps | Evaluate Astra proposals, aligned/refined through the geometry tools |

This is a division of work, not a blanket endorsement of the existing detector. Current SAM integration uses narrow heuristic candidates; SAM 3 itself also supports text and visual prompts. Its official repository supplies custom-data fine-tuning code and an example of a multimodal model using SAM as a tool. Those are options for later evaluation, not proof of card-defect performance.

The earlier explanation must not be interpreted as “SAM can never learn.” Its weights stay fixed in the current inference path; external Memory can change proposals and decisions, and offline fine-tuning is technically possible. Likewise an Astra API request does not automatically teach all later calls. Immediate system learning requires retrieving relevant saved corrections/examples into the next request or tool call. Reusing the same API key does not implement that knowledge loop.

Map drafting is a plausible Astra task, but exact map boundaries still need image-coordinate tools and evidence. One damaged example must not teach the system to exclude that damage as normal artwork on every later card. An existing deliberately reviewed map/correction can establish the reference; no new universal manual approval stage is proposed.

The published SAM 3.1 speed figure concerns multi-object video tracking, so it is not evidence that upgrading this still-photo grader will deliver the same benefit. First compare the actual task. Initial model comparison should measure missed defects, false positives, type accuracy, outline/area accuracy, grading impact, elapsed time and human correction effort. Include small/faint, long/large, reflective and heavily printed examples. Keep source pixels and scoring rules consistent across candidates.
