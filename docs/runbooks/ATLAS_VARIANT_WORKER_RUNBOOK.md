# Visual variant worker release requirements

This is a preparation guide. It does not authorize a migration, role change, credential change, process start or provider request. The current deployed baseline remains recorded in MASTER_PRODUCT_CONTEXT; the visual-variant feature is not enabled by this document.

The dedicated process runs `packages/atlas-connected-manual/scripts/serve-variants.mjs`. It never starts the normal grading queue. Its database URL must target the same staff database/schema as the main manual service, use a different nonprivileged role, and set `connection_limit=1`. Keep the main manual pool at4. Create a new role from `variantWorkerRoleSQL` and apply the exact SQL from `variantWorkerGrantSQL`, both in `packages/atlas-connected-manual/src/variant-worker-grants.mjs`, only after the registered staff migration76→77 and preservation/no-op rehearsal are reviewed. The template intentionally leaves the role NOLOGIN; the release operator provisions its credential through the existing protected transport, without printing or persisting it in a receipt.

Do not reuse `manualGrantSQL`, `intakeGrantSQL` or `connectedGrantSQL` for this role. Those are serving grants and include human/state-changing capabilities the worker does not need. The narrow worker needs SELECT on current cards/intake/history/learning, source-qualified machine authentication, variant job/cache/outbox effects and the existing durable defect-analysis repository for explicit identity-change rechecks. UPDATE(id) on the two card tables exists only because PostgreSQL row locks require an UPDATE privilege: existing immutable-id and required-revision triggers reject actual mutations, and the worker receives no revision/content UPDATE. Prove this in the owned PostgreSQL rehearsal before release. There is no worker INSERT on manual actions, approvals, variant confirmations, public publications, market jobs or learning publications.

Before activation, validate every required grant individually, role connection cap1, no role membership/ownership/create privileges, no human/public mutation privileges, exact source/image bindings and environment. The worker's cold serving constructor must not require automatic-market write grants; disable that unrelated worker flag in its process environment while keeping the main process automatic sold-comps setting unchanged. Existing active learning reads stay enabled so identity rechecks use current learning releases; the variant process must not start the learning publication worker.

Constrain one worker and one in-flight comparison, plus explicit CPU/memory/native image-thread limits. A separate process and database pool do not by themselves isolate host CPU or provider account rate limits. Record whether the provider credential shares an account/rate budget; qualify and reserve capacity before enabling. Reference source metadata acquisition is separately bounded/cached. Serving GET routes load saved evidence and retained reference bytes only, with no catalog discovery or model call.

The release sequence is: append a planned SESSION_LOG entry; run reviewed registered migration77 and exact-role grants with full old-row/control/ledger preservation and second no-op; qualify the native image and the new web UI; launch the constrained process cold against its exact release binding; verify schemas/grants/readiness and source-bound signed read denials; restore admission only under fresh approved release controls. Root owns all production execution. No existing approvals are backfilled into required human confirmations. Automatic sold comps remains bound to each new real human approval.

Operational recovery is evidence-based. An uncertain photo-model dispatch stays UNKNOWN and cannot be repurchased by refresh. Saved responses retry projection locally. Definite pre-dispatch failure can receive an explicit new reference generation. A READY reference refresh preserves the old result and reuses its suggestion when source/identity/catalog hash match. The source cache may expire for new acquisition while exact old source/image evidence remains readable through `getRetained(key,sha256)`. Expired sixth-attempt leases settle terminal states instead of spinning. Human UNRESOLVED affects only the current card; an expert MANUAL decision requires explicit parallel plus observed physical features.

An identity change retains reusable photos/frames/quads/findings, invalidates identity-sensitive approval, clears geometry confirmation for renewed human border review, and requests fresh compatible analysis. The original full report and approvals are immutable. Approval requires the current exact human variant choice, current geometry confirmation, exact READY analysis receipt, matching frame/profile/identity fence and all fresh proposals reviewed. An explicit reconfirm after a proved refusal or a saved READY analysis whose prepared frames are now incompatible may mint a new recheck action. Stale READY recovery requires an exact current-card/request/response fence prepared outside the transaction and verified at commit; an UNKNOWN recheck retains its old action. Do not describe this as a universal cosmetic identity edit or a full rerun of the original card-type-map pipeline.

Photo references require a separate explicit rights permission on a concrete human confirmation. The ordinary contribution stays metadata-only. Any private-photo extension must bind exact source/identity/action and permission, submit a distinct idempotent reference proposal, and leave catalog publication and license acceptance to human review. No checkbox or saved suggestion establishes global catalog authority.
