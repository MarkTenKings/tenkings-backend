# Ten Kings Vault Machine

This package is the sole local writer and immediate authority for Vault V1. Its payment boundary supports separate machine-selected Nayax Spark and Stripe Terminal test routes. Spark uses Remote Start PRE_SELECTION through an authenticated callback inbox; Stripe retains its server-driven test PaymentIntent integration. Physical terminal and live payment acceptance remain open. See [Spark integration and configuration](../../docs/vault-v1/NAYAX_SPARK_V3_REVIEW_2026-10-07.md).

Linux/Omarchy packaging targets pinned Node22.23.2 and native better-sqlite3 11.10.0; Node20 remains supported for the existing local compatibility/preview tests. See [Linux appliance setup](../../docs/vault-v1/LINUX_APPLIANCE_2026-09-16.md). The CLI requires a unique machine UUID, a pinned Ed25519 configuration public key, separate protected callback/maintenance tokens, an absolute persistent database path, exact loopback origin and build-stamped app/source identity.

Adapter selection is explicit: `VAULT_PAYMENT_ADAPTER=MOCK|STRIPE_TEST|NAYAX_SPARK_TEST` and `VAULT_CONTROLLER_ADAPTER=SIMULATOR|WAVESHARE`. Missing or unknown selections fail. Test payment modes cannot compose a physical controller. `STRIPE_TEST` requires a Stripe test key, test location, and configured reader ID. `NAYAX_SPARK_TEST` requires a protected absolute `VAULT_SPARK_CONFIG_PATH`, assigned sandbox token/signing secrets and confirmed sandbox/PRE_SELECTION/USD bindings; it polls the authenticated cloud callback inbox. The [Spark environment example](../../deploy/vault-linux/templates/machine.spark.env.example.json) and [binding example](../../deploy/vault-linux/templates/nayax-spark.test.example.json) start with unusable placeholders and false confirmations. WAVESHARE requires `VAULT_WAVESHARE_CONFIG_PATH` containing the reviewed device, firmware, mapping, and qualification bindings; startup only reads identity and status. Ordinary physical commands require a qualified signed schema 2 profile, and uncertain output stops later commands. The [bench CLI](../../docs/vault-v1/WAVESHARE_INTEGRATION_2026-09-16.md) handles supervised characterization before customer service qualification.

The maintenance endpoint is `POST /api/v1/internal/maintenance`, with contract/origin headers, separate `X-Vault-Maintenance-Token` and `{ "action": "status" | "enter" }`. Its normal response envelope contains `data`. Entry freezes new HTTP writes, drains existing activity/runtime, rechecks durable payment/command/staff work and retains service lock across a planned restart. A healthy listener alone is not restart authority. No SDK flag or maintenance operation clears a physical uncertain-output journal automatically.

Core invariants are enforced in SQLite transactions: immutable checkout snapshots and provider/device bindings, reservations, verified captured-payment-to-fulfillment commit, deterministic command intents, pessimistic unknown dispatch boundary, all-original-paid-door group retry, per-door restock outcomes, append-only events, and ordered outbox delivery. Changing the selected provider cannot reconcile or restart another provider's pending sale. Unknown Spark requests never create replacement payments. Same-request replay is bounded and disabled unless the assigned vendor profile explicitly confirms its safety; recovery holds force read-only reconciliation. Paid voids require fresh exact-sale Admin approval and use a separate durable ledger, leaving original capture and door allocation unchanged.

Signed configuration schema 2 uses explicit versioned machine profiles with stable door IDs, separate printed labels and geometry, and controller endpoint/channel mappings. Public ordering follows the profile, while every sale and command pins the original label/address/profile digest. Historical schema 1 remains readable with its original 150-door identities, mappings and signed bytes. Local SQLite schema 4 adds immutable payment bindings while retaining retired doors and immutable sale, command, restock and certification history. Existing pending payments without reliable provider proof require review; this software change does not migrate an installed machine.

Topology changes require the local Technician or Admin to review the exact pending configuration and confirm every compartment is empty and serviced doors are closed. Activation rejects stock, active carts, transactions, unfinished payments/commands, restocks or certification. It ends the staff session while preserving service lock; authentication and safe exit are required before public operation. Retired stable IDs cannot be rebound to different compartments or addresses. A `FILLED` outcome under a schema 2 profile requires explicit confirmation that the actual packaged product fits the compartment. Synthetic dimensions and mappings are software fixtures and never qualify a physical cabinet.

Use the disposable mock demo from the repository root:

```sh
env PATH=/opt/homebrew/opt/node@20/bin:/opt/homebrew/bin:/usr/bin:/bin pnpm vault:demo -- --doors 72
```

For owner UI review, run `pnpm vault:preview` with Node 20. It opens a disposable 72-door configuration with eight sample Sports/Pokémon products, stocked through the ordinary staff/restock HTTP workflow. Open the printed loopback URL, choose a product and door, checkout, start simulated payment and try retrieval/retry/Done. It does not connect to a payment terminal or lock. Stop and rerun to reset the disposable inventory. Sample prices, tax, images, dimensions and addresses are not production configuration.

For SER bringup, the direct simulator launcher also accepts the pinned Node22 runtime after native dependencies are built on Linux. A source-only candidate bundle may pass `--source-manifest /path/to/candidate-source.json`; every listed source digest is checked and the run is stamped `CANDIDATE_SHA256:<manifest digest>`. A dirty local checkout is stamped `UNCOMMITTED_CANDIDATE`. Neither is a trusted40-character commit or can satisfy physical certification provenance. The signed appliance release builder still requires a clean reviewed commit. See [SER bringup](../../docs/vault-v1/SER_BRINGUP_2026-09-16.md).

The demo also supports `--doors 125`, `--stocked` and an automated `--smoke` run. A stocked smoke checks initial inventory, public checkout, exactly one initial unlock for the selected door, one requested retry for that same door, serial command dispatch and event synchronization. It prints its loopback URL and temporary test staff credentials (`simulator-tech`, PIN `123456`), uses generated local keys and mock cloud/payment/controller boundaries, and removes the disposable session on exit. Staff entry is ten taps on the upper-left service corner in the original interface, or upper-right in the cinematic preview. These fixtures do not describe physical wiring. The standalone machine CLI's optional `VAULT_SIMULATOR_MAPPING_PATH` supplies a reviewed JSON simulator address array for a schema 2 profile; absent that input it supports only the historical schema 1 mapping. No address is derived from a door label or screen position.

The [Stripe UX700 integration review](../../docs/vault-v1/STRIPE_UX700_INTEGRATION_REVIEW_2026-09-28.md) tracks the server-driven test path and remaining physical acceptance work. Omarchy is the Linux direction. Appliance packaging is a candidate; installation on the actual SER remains unobserved.

Encrypted backup/restore is bounded to 256 MiB per SQLite snapshot and verifies database and foreign-key integrity. Support exports use a fresh directory, include only redacted metadata and bounded log tails, and exclude database and credential files. The historical Windows implementation remains incomplete. The Linux candidate adds protected configuration, service packaging and guarded updates; installed hardware qualification remains open. LIVE dispatch remains rejected.

Windows files under `windows/` are digest-verifiable service/install/update/rollback/support artifacts. They are source artifacts only; this implementation did not install, restart, or update a Windows service.

### Cinematic customer preview

`pnpm vault:cinematic` builds and starts the disposable stocked simulator with `?experience=cinematic`. This three-door 3D gallery is restricted to synthetic certification data; it uses the existing cart/payment/recovery service. See [the cinematic preview handoff](../../docs/vault-v1/CINEMATIC_PREVIEW_2026-09-10.md) for the running link, tests, artwork and pending SER5 measurements.

For a stable local preview URL, the disposable simulator also accepts `--port 55497`, for example `pnpm vault:cinematic -- --port 55497`. It still binds only to 127.0.0.1. Omit the flag (or use 0) for an available random port; an occupied port fails rather than stopping another process.
