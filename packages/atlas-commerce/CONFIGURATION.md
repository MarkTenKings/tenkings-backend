# Customer commerce configuration

These [private service](config/private-service.env.example), [customer web](config/customer-web.env.example) and [public web](config/public-web.env.example) and [staff web](config/staff-web.env.example) files are cold templates. They contain no credential values. The private file is separate from the existing manual service environment; the web templates supplement existing customer authentication and public report settings.

Populate a copy only in protected secret custody. Do not commit populated files or send credentials in chat. The server receives Stripe, the configured shipping provider and receipt-provider credentials; the customer web app receives only its own signed transport key and upload origin, and the public web app receives only its directory key. Keep every activation flag false until deployment controls and real providers are qualified.

Run the static checker with Node20 or newer using a protected environment file:

```sh
node --env-file=/absolute/protected/private-service.env packages/atlas-commerce/scripts/check-configuration.mjs
```

The checker makes no network request and prints only fixed status labels and missing/invalid key names. `COLD` means dispatch is disabled; missing keys are expected. `INCOMPLETE` means enabled settings cannot qualify. `READY_FOR_PROVIDER_QUALIFICATION` means the selected payment mode passes local shape and mode checks only. In separate-payment mode this qualifies the grading configuration; later shipping has its own carrier, measurement and shipping-tax gates. It does not authenticate accounts, validate tax registration or classifications, confirm receipt-sender approval, measure a package, verify the database binding, or qualify a kiosk. Missing webhook configuration is reported even though provider construction alone permits a cold webhook.

The selected mail clock starts at actual ATLAS receipt; the selected future shipping purchase charges both legs. Configure those choices explicitly as `ATLAS_RECEIPT` and `BOTH_LEGS`. Tax codes, sender identities, merchant IDs, measured package plans, kiosk addresses/routes and device IDs must come from real account and operational information. Test payment mode cannot be mixed with a production shipping adapter. Existing SMS verification credentials do not imply an approved receipt messaging service.

Each private `CommerceControl.shippingPlans` entry must contain a `packingPresetId`, `shippingServiceCode`, an exact integer `cardCount` from1–100, and a nonempty sourced `measurementReference`. The measurement reference attests to the configured plan; the application does not independently verify a physical measurement. Measure and configure each supported count and each charged direction independently. A larger count never inherits a smaller package's weight. Duplicate preset/service/count choices are refused.

For the existing `atlas-measured-shipping-plan-v1` format, `validFrom` and `validUntil` are explicit canonical UTC timestamps (`YYYY-MM-DDTHH:mm:ss.sssZ`) permitting new quotes for at most24 hours. These are configuration admission limits, not carrier-rate validity or customer turnaround promises. The rate provider and saved quote keep their own expiry, and a quote cannot outlive the plan. Expired or mismatched plans disappear from customer options and are refused by both service and SQL. No environment-file checker alone qualifies these database records.

Each required v1 `legs.INBOUND` / `legs.RETURN` carries a `shipDateTimeZone` with a qualified IANA origin timezone and the exact FedEx `requestedShipment`. That request contains a real calendar `shipDatestamp` which has not passed in that timezone, the selected matching `serviceType`, configured pickup/packaging/billing, and exactly one package with positive measured weight and positive integer dimensions with their units. Supply the actual ATLAS recipient for inbound and actual ATLAS shipper for return; omit the unknown customer party, which is derived only from the confirmed checkout profile. Neither a future return date nor a mailing destination is invented. Actual FedEx service/date acceptance is still required.

The complete selected plan and final customer-bound carrier requests stay in the immutable internal quote; customer responses expose only the existing option/display fields. SQL rejects a changed plan, count, measurement, weight, date, service or customer party even if a caller recomputes its content hashes. For v1 shipments, label creation checks the original date again before claiming a pending effect. A date that has passed leaves that effect pending with `SHIPPING_DATE_EXPIRED` for operational resolution; it never silently changes a paid shipment, creates another effect or repeats an uncertain provider call.

For sustainable prepaid shipping, `atlas-measured-print-return-plan-v2` keeps the same exact measured count, package, service, billing, ATLAS parties and `measurementReference`. It requires canonical `validFrom`, omits `validUntil`, and remains usable while that exact policy is configured. Replace or remove the configured policy when its measured facts change. Every charged leg must carry `labelDatePolicy: "FEDEX_PRINT_RETURN_CREATION_DATE_V1"`, a qualified `shipDateTimeZone`, and these native FedEx special services:

```json
{
  "specialServiceTypes": ["RETURN_SHIPMENT"],
  "returnShipmentDetail": { "returnType": "PRINT_RETURN_LABEL" }
}
```

Place these fields inside `requestedShipment.shipmentSpecialServices`. A v2 template must omit `requestedShipment.shipDatestamp`; the server fills it from the quote creation instant in that leg's configured timezone before requesting the rate. The quote remains valid for at most15 minutes, or less when tax/carrier rates expire earlier. SQL independently derives that date from canonical, recent `quote.createdAt` and requires the exact configured template plus confirmed customer party. Configuration stability never extends a saved price quote.

Paid quote snapshots, shipment request bytes, and original `:fedex:INBOUND:v1` / `:fedex:RETURN:v1` effect IDs remain unchanged. Only requests carrying both the explicit policy and native printed-return semantics may reach label creation after their saved date has passed. FedEx's [Ship REST schema](https://developer.fedex.com/wirc/json/api_groups/Ship/Shipment-Resource.json), `RequestedShipment_1.shipDatestamp`, documents using the current date for an omitted or past date. ATLAS does not rewrite the request, replay an uncertain shipment, or mark actual custody from label creation. Existing v1 requests keep their former date rules.

The [Ship API documentation](https://developer.fedex.com/api/en-us/catalog/ship/v1/docs.html) documents printed return labels as usable later, including processing/repair workflows. This is a provider-native label type, not an assumption that ordinary outbound labels can wait through grading. Before enabling a real policy, qualify its actual FedEx account, service, measured packages and both directions using account rates and Validate Shipment. These local contracts and synthetic tests do not prove the account's entitlement or the provider's acceptance. The customer receipt distinguishes the directions and offers the inbound label for mailing to ATLAS; the return label remains for ATLAS fulfillment.

Follow the source-bound deployment, least-privilege database and real-provider checks in [customer release readiness](../../docs/atlas/audits/2026-09-24/customer-release-readiness.md). Credentials alone never enable paid checkout: the exact immutable merchant binding, deployment-bound customer controls and measured shipping plans must also match.

Mail-in fulfillment uses the existing staff **Customer operations → Paid submissions** page. Set `ATLAS_MANUAL_DEALER_OPERATIONS_ENABLED=true` in both the staff web candidate and private manual runtime, alongside the existing manual feature and reviewed manual-serving role's `atlas_dealer.staff_call` grant. This internal operations switch does not create a dealer location, enable kiosk intake, or require a dealer registry entry. It remains separate from customer commerce activation. The staff page stays unavailable while its display switch is false.

Migration `20261008001000_atlas_stable_print_return_shipping` extends that existing staff function without widening its grants. Authenticated reviewers can download the already-saved return PDF from a paid mail-in order; the roster contains only label status. The exact `GET /api/staff/manual-connected/dealer-operations/orders/:orderId/return-label` checks the paid order, RETURN effect identity, provider request hash, PDF signature, size and byte hash. It never creates a label, repeats an effect or records mailing. A retained custody mutation does not block this separate read. Record the actual mailing in each card's existing custody workflow after physical dispatch.

The release must qualify both private ingress layers for the operations roster and exact return-label GET, alongside the existing authenticated custody/binding POST routes needed for mail-in operations. Preserve decoded-path and raw-URI admission, query/trailing-slash refusal, signed private transport and reviewer authentication. The previous cards-only Caddy matcher does not cover these routes; enabling the feature switches alone cannot repair that ingress limitation. The narrow return-label response sends the verified PDF as binary with its SHA-256 header, bounded to 4 MiB end to end. This fits Vercel’s [4.5 MB response payload limit](https://vercel.com/docs/functions/limitations) without base64 JSON expansion. The staff proxy and browser reader admit this MIME only for the exact return-label GET; other manual JSON responses retain their existing limit.

The public web switch `ATLAS_PUBLIC_CUSTOMER_FUNNEL_ENABLED=false` preserves the previous service text and contact directory and makes no private kiosk-directory request. Enable the new price/checkout marketing and kiosk directory only after the new customer deployment is promoted and the complete flow is qualified. This display flag never enables private provider dispatch.

## Separate grading and shipping payments

The owner-selected mail-in offer is `ATLAS_COMMERCE_MAIL_SHIPPING_PAYMENT=SEPARATE_PAYMENT`. Set the same `shippingPayment: "SEPARATE_PAYMENT"` in the private, source-bound `CommerceControl.terms`. The default `UPFRONT` preserves older deployments and saved quotes; never reinterpret an existing paid receipt. New mail-in checkout charges $40 per card plus its actual Stripe Tax calculation. Card-shop pricing remains $50, with its existing eligibility and operations gates.

Initial grading checkout requires its actual merchant, grading tax classification/sourcing, verified receipt email, capacity and customer profile. It does not require a carrier credential, shipping tax classification, package plan or customer package dimensions. Its safe quote explicitly carries `shippingStatus: "UNQUOTED_UNPAID"`, no shipping legs, and `terms.shippingPayment: "SEPARATE_PAYMENT"`. Numeric shippingCents=0 means no shipping in **this charge**, never free future shipping. The receipt tells the customer to return to the saved order to review and pay for shipping when available. Turnaround still starts at physical ATLAS receipt, not grading-fee payment.

Migration `20261008004000_atlas_deferred_shipping_payments` adds separate `CommerceShippingQuote`, `CommerceShippingPayment`, `CommerceShippingReceipt` and `CommerceShippingProviderEvent` evidence. The original grading `CommerceOrder` receipt stays immutable. Shipping payments never insert a second grading payment, grading order, dealer commission or weekly capacity reservation. New tables and helper functions remain owner-only; authenticated customer actions use the existing private service boundary.

Later shipping checkout uses the paid order's frozen, verified contact/address and exact cards, plus the currently configured measured package plans. Before it can quote, qualify the actual carrier credentials, real receiving address, supported carrier/service, measured return package for that card count, customer's inbound measurements and explicit shipping tax classification. Keep `ATLAS_COMMERCE_MAIL_CHARGED_LEGS=BOTH_LEGS`. Rates and tax remain real provider results; neither identity-verification delays nor missing measurement/configuration create a substitute rate. Insurance remains disabled.

Customer routes under `/commerce/orders/:orderId/shipping` provide checkout, quote, explicit Pay and reconcile through signed private operations `commerce-shipping-checkout`, `commerce-shipping-quote`, `commerce-shipping-pay`, and `commerce-shipping-reconcile`. A shipping quote has `purpose: "SHIPPING"`, `orderId`, zero grading subtotal, actual shipping amounts and applicable shipping-only tax. The customer must approve its own Stripe form; no saved payment method is automatically charged. One active shipping attempt per order and one account/request identity prevent duplicate intents. UNKNOWN outcomes retain the original attempt and use provider retrieval, including the same existing Stripe webhook. Current missing carrier/plans do not block recovery of an already-created payment. Confirmed provider cancellation permits a new quote; browser errors never imply cancellation.

Order reads add `shippingPayment` with state, safe active attempt, and the separately paid receipt. Shipping payment responses also include their safe frozen `quote` so a resumed payment form can show the exact amount/legs without requoting. Immutable provider IDs, requests, credentials and payment evidence remain private. Labels are enqueued only in the transaction confirming the separately paid shipping amount. The original both-leg selected rate is retained; later actual return-label cost is audited without an automatic customer surcharge. Existing explicit staff return preparation and physical-custody rules remain unchanged.

`EMAIL_SHIPPING_RECEIPT` confirms the second payment. `EMAIL_LABEL_READY` is enqueued once, atomically, only after the inbound label reaches SUCCEEDED with a PDF signature, bounded size and matching SHA256. It links to the authenticated account, never an exposed label URL or email attachment. UNKNOWN label responses create no notification. The durable outbox prevents automatic repeat sends after an uncertain send; provider acceptance is not delivery. The safe `labelReadyEmailEnabled` capability is true for deferred paid-grading orders: the eventual validated inbound PDF will enqueue the email. This does not imply shipping has been quoted or paid. No shipping-ready notification is sent merely because carrier configuration becomes available.

## Standalone ShipStation API shipping

Migration `20261008002000_atlas_shipstation_shipping` adds the standalone [ShipStation API](https://docs.shipstation.com/api-overview), formerly ShipEngine. Requests use `https://api.shipengine.com/v1`; Companion API credentials do not apply. Set private `ATLAS_COMMERCE_SHIPPING_PROVIDER=SHIPSTATION`, `ATLAS_COMMERCE_SHIPSTATION_API_KEY`, and `ATLAS_COMMERCE_SHIPSTATION_ENVIRONMENT=PRODUCTION` for live Stripe or `SANDBOX` for test Stripe. Sandbox keys start `TEST_`. Keys never enter customer responses. FedEx remains the default when the provider selection is absent; retain valid FedEx settings while historical FedEx effects need fulfillment or reconciliation. A new provider selection never rewrites those effects.

Configure a separate `atlas-measured-shipstation-plan-v1` plan for every supported carrier/service/card count. Its top-level fields are `provider: "SHIPSTATION"`, `fulfillmentPolicy: "INBOUND_AFTER_PAYMENT_RETURN_WHEN_PREPARED"`, `inboundPackaging: "CUSTOMER_MEASURED"` or `"CONFIGURED"`, the actual `carrierId` and `serviceCode`, unique customer `packingPresetId` / `shippingServiceCode`, exact `cardCount`, sourced `measurementReference`, canonical `validFrom`, and customer display `label`, `packaging`, `carrierLabel`, `serviceLabel`. It has no `validUntil`. The synthetic structural example in [shipstation-fixtures.mjs](test/shipstation-fixtures.mjs) is test data and must never be installed as a production measurement or address.

Both `legs.INBOUND` and `legs.RETURN` contain `provider: "SHIPSTATION"`, `labelDatePolicy: "SHIPSTATION_FULFILLMENT_DATE_V1"`, the leg origin's `shipDateTimeZone`, and a `shipment`. Each shipment holds the exact `carrier_id`, `service_code`, `confirmation`, `insurance_provider: "none"`, plus the actual ATLAS `ship_to` on inbound or `ship_from` on return. Omit customer parties and `ship_date` from configured templates; the service binds the confirmed customer and quote date. Parties contain name, phone, address_line1, optional address_line2, city_locality, state_province, postal_code, country_code US, and address_residential_indicator.

For customer-measured inbound shipping, omit inbound `packages`; checkout requires the customer's measured `inboundPackage` with positive weight and dimensions. Weight units are pound, ounce, gram, or kilogram; dimension units are inch or centimeter. Every configured return leg requires exactly one `{package_code: "package", weight, dimensions}` measured package for that exact count. Both layers reject over 150 pounds, longest side over 108 inches, or length plus girth over 165 inches; individual carrier services still impose their own acceptance limits. These broad parcel bounds follow the published [UPS limits](https://www.ups.com/us/en/support/shipping-support/shipping-dimensions-weight) and do not assert an account's entitlement. No size, weight, card-count scaling, pickup policy, or mailing date is guessed.

An exact fresh quote calls the selected carrier/service for both directions and sums documented shipping, confirmation and other rate charges. Customer responses show each charged leg, carrier/service and measured inbound package. Selecting another service or editing measurements requires a fresh quote. Rate IDs, shipment IDs, private requests and credentials stay internal. Optional insurance is disabled: ParcelGuard coverage for customer-owned grading cards, grading damage or diminished value has not been established. Neither the application nor these fixtures claim that coverage.

After confirmed payment, only the inbound label becomes immediately eligible. The stored return charge remains fixed; **Customer operations → Paid submissions → Prepare return label** becomes eligible after every order card's latest actual custody is ATLAS_RECEIVED and every card has a linked approval. Exact `POST /api/staff/manual-connected/dealer-operations/orders/:orderId/return-label` accepts only `{requestId}` and uses existing reviewer authentication and durable mutation reconciliation. The roster returns `preparedRequestId` for that exact action. Replaying it cannot redate or recreate fulfillment. Both private ingress layers must permit this exact POST as well as the existing return-label GET. Preparation and label purchase never assert MAIL_DISPATCHED.

Immediately before claiming a new ShipStation effect, the worker materializes the current local shipping date, retains all paid address/package/carrier/service facts, and uses a still-valid rate or obtains a fresh rate for that exact shipment. SQL durably records the dispatch request and rate before any paid label call. The customer is never surcharged for fulfillment price changes; original paid rate and actual purchased provider cost remain separate audit facts. Label purchase uses [the saved rate ID](https://docs.shipstation.com/apis/shipengine/openapi/labels/create_label_from_rate.md) and a deterministic external shipment ID. Inline PDF bytes come from documented `label_download.href`. A lost/invalid response remains UNKNOWN and only [reads that external ID](https://docs.shipstation.com/apis/shipengine/openapi/labels/get_label_by_external_shipment_id.md), at most five backoff attempts; it never repeats the purchase. An unresolved UNKNOWN requires operational investigation.

Tracking polling is optional and defaults off. Set `ATLAS_COMMERCE_SHIPSTATION_TRACKING_ENABLED=true` only after confirming the account's [tracking entitlement](https://docs.shipstation.com/apis/shipengine/docs/tracking/tracking). The worker reads a maximum of five purchased labels per batch, with a durable six-hour interval and no further polling after delivered. Tracking updates are bound to the exact provider label/tracking number and do not change label results, paid prices, or custody. Synthetic tests establish local contracts; actual carrier rate acceptance, account mode and entitlements still require account qualification before activation.
