# Weekly ATLAS card capacity — local implementation, October 1, 2026

Owner direction: capacity counts **cards**, with independent mail-in and authorized-card-shop pools. A 20-card batch uses 20 spots; there is no weekly customer cap. Existing 100-card intake batch limits remain separate. The reset boundary is Monday **00:01 America/Los_Angeles**, with local daylight-saving offsets calculated at each boundary. The suggested 500/1000 quantities were examples, not approved quotas.

`sql/weekly-capacity-proposal.sql` is registered byte-for-byte as source migration `20261001001000_atlas_weekly_card_capacity`. The migration is **unapplied in production**; only owned disposable fixtures have executed these bytes. Both quota configuration rows start NULL. A missing quota is `NOT_CONFIGURED`, with null counts—not zero remaining, a guessed limit, or a live countdown. A failed/disabled service or missing schema is unavailable. Operator configuration is a separate release-owner action; no configuration/admin grants were added.

## Durable behavior

The existing `CommercePayment` insert acquires an atomic hold through a database trigger before the transaction returns permission to dispatch the payment provider. The hold uses the saved quote's card roster length, not a browser count. The trigger locks the channel/week row and computes occupancy from reservation rows, so concurrent submissions cannot oversell. No mutable remaining counter exists. Quotes and photo drafts allocate nothing.

`DISPATCHED`, `UNKNOWN`, `AWAITING_PAYMENT`, and `PROCESSING` retain their hold. An absent browser, elapsed quote, or missing provider result never frees a potentially payable reservation. The existing provider-retrieval cancellation boundary produces `CANCELED`; only that terminal transition releases the hold. `PAID` changes HELD to CONSUMED in the same transaction as the existing order/receipt commit. Replays do not consume again. If the order transaction rolls back, the capacity transition rolls back too. An abandonment cleanup must first establish a provider-confirmed cancellation; no automatic time-based hold release was added.

The public pool `DEALER_DROP_OFF` maps from existing commerce channel `KIOSK`, without adding terminal/payment-device assumptions. Mail and shop pools cannot borrow from one another. A configured quota is frozen when its first payment creates that weekly window; configuration changes affect a subsequent new window. Configuring NULL later does not alter a frozen current window. All prior windows, paid cards, and unresolved holds remain saved. A new admission week does not mark an old order complete or remove its backlog. Operations still need to set quotas consistent with actual staffing and outstanding work.

Historical payments created before this additive feature remain readable/confirmable and are not silently backfilled into fabricated capacity evidence. Release acceptance must inspect any outstanding legacy attempt before activating new capacity.

## Read contract

Anonymous GET/HEAD `/api/capacity` uses the existing signed customer-service directory capability. The new `weekly-capacity` operation is read-only and cannot admit payment mutations. The narrow private SQL gateway validates existing release/control bindings before calling `weekly_capacity_snapshot()`. Customer roles receive no capacity-table or general function grants.

Response: `{version:'atlas-weekly-capacity-v1',unit:'CARDS',timeZone:'America/Los_Angeles',resetLocalTime:'00:01',weekStartsAt,resetsAt,asOf,pools:[{channel,state,quotaCards,heldCards,acceptedCards,remainingCards}]}`. Pool channels are `MAIL_IN` and `DEALER_DROP_OFF`; states are `AVAILABLE`, `FULL`, or `NOT_CONFIGURED`. Only aggregate counts are exposed. All fields are allowlisted and internally checked. API reads are no-store; a client must refresh at reset/return-to-tab and after checkout rather than decrement an authoritative server counter locally.

Checkout includes the same safe capacity snapshot and `WEEKLY_CAPACITY_NOT_CONFIGURED` / `WEEKLY_CAPACITY_FULL` blockers for new payments. Existing payment reconciliation and paid receipt recovery remain accessible. Availability is advisory until the atomic payment hold succeeds. A last-spot race returns 409 `WEEKLY_CAPACITY_FULL`; unconfigured quota returns 503 `WEEKLY_CAPACITY_NOT_CONFIGURED`. Provider logic, physical custody, shipping fees, and turnaround claims are otherwise unchanged. Mail-in turnaround begins from the owner's actual ATLAS-receipt event, not capacity reservation/payment or the reset.

## Customer-phone shop payment transition

The owner’s corrected shop flow pays on the customer’s own phone. `sql/customer-phone-proposal.sql`, registered byte-for-byte as source migration `20261001002000_atlas_customer_phone_payments`, is an exact additive replacement of the existing provider gateway and its bounded display projections. Newly saved immutable quotes carry `terms.paymentFlow='CUSTOMER_PHONE'`. Both new MAIL_IN and KIOSK quotes use the existing online `card` intent path; no Terminal reader is reserved. A shop registry still requires its real dealer, revision, address and pickup/return schedule, but reader/printer IDs become optional through the separate dealer handoff migration. Only the owning `AWAITING_PAYMENT` response receives its original client secret and publishable key. Public SQL recovery carries the safe flow flag and no secret. New phone-shop orders retain the SMS/tax outbox, create an email receipt when the saved contact has a valid email, and skip the old printer-label effect; physical handoff is the scoped dealer QR receipt, never the payment event.

Legacy KIOSK quotes without this flag retain their original `card_present` method. Fresh payment dispatch from such a quote is refused with `PAYMENT_FLOW_CHANGED`, requiring a current quote. Existing dispatched/unknown/awaiting/processing/paid attempts return their saved attempt before that new-quote gate. They keep their reader ID, provider ID, quote hash, receipt terms and prior package effect. No in-flight Terminal payment is canceled, reissued or converted silently. A legacy payment cannot be confirmed with `card` evidence; a phone payment cannot be confirmed with `card_present` evidence. The gateway and JavaScript provider contract independently enforce that distinction.

New mail-in quote admission now requires `mailClockStart='ATLAS_RECEIPT'`, matching the owner’s promise that the turnaround starts at physical ATLAS receipt. Historical paid receipt terms remain immutable. The outstanding choice of charged shipping legs is still supplied by the existing explicit owner configuration; this feature does not invent it.

`frontend/atlas-customer/scripts/validate-private-commerce-postgres.mjs` qualifies the exact capacity → phone → handoff bytes with actual synthetic SMS sessions, verified photo pairs, tax/quote bindings and private SQL roles. Test observations are synthetic; they qualify no real charges, sends, wallet domains, saved-card vault or hardware operation. ## Shop contact and tax context

Migration `20261001005000_atlas_shop_contact_profile` is the exact registered copy of the intake owner's `packages/atlas-customer-intake/sql/shop-profile-proposal.sql`. Fresh shop intake accepts a name with optional email; the verified account phone remains server authority. The stored intake method chooses the validator. Mail-in still requires its complete return profile and email. A compact contact save merges into an existing account profile, preserving its return address; explicitly blank email removes the mutable account email while an omitted email preserves it. Neither save changes an existing paid quote, receipt, or unresolved payment snapshot.

New KIOSK phone quotes preserve the exact compact contact without inventing home addresses. Tax calculations use the configured shop registry address and no shipping charge. This implements the existing `MAIL_RETURN_ADDRESS_KIOSK_LOCATION` sourcing contract; real merchant tax registration and jurisdiction qualification are still external release work. When email is absent or blank, the new phone-shop order has only its SMS receipt and tax transaction effects. Legacy terminal orders and mail-in orders retain their existing effect rules. Email/SMS sender configuration remains required by the shared provider construction; optional customer email does not assert that a sender is already approved or live.

`inspectCommerceConfiguration(env,{channel:'KIOSK'})`, also available through `scripts/check-configuration.mjs --channel KIOSK`, can inspect shop-only construction without FedEx/mail terms or terminal/printer prerequisites. The default ALL inspection continues to require both routes. Both return only key names and static readiness, never live eligibility or credentials. Private commerce acceptance against the full registered 95-public/67-staff migration chain passed 14 groups with compact no-email shop checkout, retained saved address, refused compact mail profile, verified SMS destination, absence of an empty email job, and original unresolved terminal replay. Every provider result was synthetic and the owned PostgreSQL cluster was stopped.
