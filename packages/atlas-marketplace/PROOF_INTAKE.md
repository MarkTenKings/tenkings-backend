# Private marketplace proof intake

This additive candidate retains real uploaded PNG/JPEG bytes privately and binds each original to its paid marketplace order, card binding, authenticated uploader and declared purpose. It does not establish physical-card identity, title, claim truth, carrier acceptance, purchased coverage or delivery merely because a file decodes. Ownership claims/history stay disabled. Grading and Ten Kings source and credentials are not used.

## Supplied configuration and actual authority

No runtime configuration or approval is invented. The enabled factory requires the same store and authority context as the marketplace service, an owned encrypted storage adapter, the actual image validator, a synchronous current readiness function, and a synchronous current actor-authorization function. These checks also apply in synthetic tests. Factory construction or a policy reference alone grants no permission.

The policy must supply id, version, environment, approvalRef, retentionRef, reviewerAuthorityRef, effectiveAt, expiresAt, retentionMs, maxObjectBytes, maxProofsPerOrder, maxRetainedObjects, uploadTtlMs and validationLeaseMs. Maximum original size is 10 MiB; accepted formats are PNG and JPEG; each order's retained plans are bounded at a configured maximum of 50; total plans are bounded by the supplied policy. Failed and abandoned plans continue consuming the retained quota. Upload plans expire within 15 minutes; validation has a durable lease and at most three original-byte attempts. These are implementation ceilings, not selected live retention periods or business approvals.

The host supplies authorize(actor,{action,orderId?,proofId?,purpose?,policyHash}). It must return true synchronously only for current permitted authority. REVIEW must separately check genuine reviewer authorization, rather than infer it from the STAFF string. The service supplies an additional authorizeCommit callback, checked before and after external work and inside commits. Its optional asynchronous refreshAuthorization callback re-reads canonical request authority before preparing, after decoding, before original publication/finalization, before reviewer commits and before private responses. It must return true; denial never authorizes a subsequent publication or review. The synchronous guard runs again after database waits. No canonical authority transaction is held across image decoding. If authority is lost after an already-authorized immutable publication, the original stays retained for separately authorized recovery; it is never deleted or replaced to hide that outcome. Actor-free intake.assertReady() separately checks the current policy window, runtime approval and actual storage readiness for persisted physical requirements. The runtime must preserve request authentication, role scope, CSRF, request admission, private response headers and byte limits. A server actor must never come from the upload body.

## Durable lifecycle and recovery

prepare(actor,{requestId,orderId,purpose,declaredType,byteCount,sha256}) allocates the immutable original identity and binds the plan. upload(actor,{uploadId,bytes}) accepts only those exact bytes. recover(actor,{uploadId}) checks that original key; it never creates a replacement. list(actor,{orderId}) returns bounded private summaries. read(actor,{proofId}) authorizes again and returns the exact decrypted bytes with their verified format and digest.

Plans move PREPARED → VALIDATING → VALIDATED → RETAINED. VALIDATED means the original decoded and its immutable manifest is recorded, but the object publication or final state commit may still be incomplete. The encrypted original is published atomically with create-only hard-link semantics and fsynced before the retained-object commit. A crash after object publication is recovered by reading and finalizing that original. A crash before publication may upload only the same planned bytes while still eligible. Invalid formats become REJECTED; transient decoder failure retains its bounded original attempt history. No new key, changed hash, order or purpose is adopted to disguise an unknown outcome.

The three durable marketplace state maps are marketplaceProofUploads, marketplaceProofObjects and marketplaceProofReviews. Existing store commit history is reused; no database/schema migration is introduced. Original manifests include exact input digest/length, full decoder receipt, uploader/order/purpose, policy hash and minimum retention date. File paths, encryption details, internal actor identities and policy/reviewer references are absent from browser summary projections. Buyers can read only their own RETURN_REQUEST originals for their own orders; sellers cannot access proof intake; staff access still requires the supplied current authority.

## Image and storage checks

proof-image.mjs runs actual sharp 0.33.5/libvips 8.15.3 full-raster decoding in a killable child. PNG framing, chunk CRC, animation markers and terminal boundaries are checked; JPEG framing/entropy markers are walked through exact terminal EOI. MIME, original hash/length, single-image dimensions and decoded raster dimensions/length must agree. HTML/SVG, truncated, corrupt, appended and mislabeled bytes are refused. Originals are not resized, re-encoded or substituted. The maximum is 16 million decoded pixels, two concurrent validators and 15 seconds; child stdout/stderr are bounded and application environment secrets are not inherited. close() terminates and joins owned decoder children and refuses new work.

This is process isolation, not a qualified OS/network sandbox or a hard bound on native-library allocation. The deployed decoder closure, process/container containment and operational load remain host qualification. No unqualified image upload should be enabled by treating synthetic test readiness functions as approval.

proof-storage.mjs implements an actual owned encrypted filesystem adapter. The host explicitly supplies a pre-existing owner-only absolute directory with no symlink parents, a 32-byte encryption key, key ID, storage ID, environment and retention reference. AES-256-GCM authenticates the bytes and manifest against storage/object bindings. Original files are created privately, synced and made read-only. Reads reject altered ciphertext, binding/hash mismatches, symlinks and permission drift. The API has no overwrite or deletion operation; passing a retention date does not erase anything. An interrupted publish can leave an encrypted staging file. The host must separately qualify durable volume placement, backups, capacity, disaster/key recovery, key rotation and the actual retention/deletion policy. Filesystem owner/root can still alter or remove files; this adapter does not claim hardware WORM retention.

## Review and business use

review(actor,{requestId,proofId,decision,reviewRef,facts?}) records one immutable APPROVE or REJECT decision about the retained artifact's suitability for its declared purpose. It does not approve the return case itself. The review checks the original again, independently checks reviewer authority, records exact original/policy binding and prevents request reuse across originals. A rejected artifact is not silently reapproved. DELIVERY review facts, if that upload purpose is used, must explicitly record deliveredAt; no image timestamp supplies physical delivery truth.

RETURN_REQUEST accepts only a retained original from the actual buyer/order/purpose. It needs no prior staff approval because the separate return-review action decides the claim. New buyer preparation and upload are allowed only within exactly 86,400,000 elapsed milliseconds of the already-evidenced actual delivery, with an exclusive deadline. Late staff observation does not extend that window. Accepted reasons remain SEVERE_DAMAGE or WRONG_PRODUCT in the unchanged fulfillment policy. ATLAS initially pays approved return shipping; allocation after review remains separate.

For staff PACK and RELEASE, each supplied main/named reference must resolve to an approved retained proof of that same purpose and order. A single reviewed photograph bundle may be referenced by more than one named field, but the reviewer remains responsible for whether it actually demonstrates each fact; software does not infer fitted inserts or seals. RETURN_REQUEST_REVIEW and REFUND_REVIEW resolve their reviewRef as approved purpose-specific proof IDs; the signed existing workflow action supplies the case decision and exact money obligations. CASE_RESOLUTION for RETURN cases requires approved RETURN_INSPECTION originals for its main and inspection refs. Non-return cases remain on their existing external evidence path. The non-synthetic service also requires the supplied external business/financial evidence validator for return decisions, refund obligations, case resolution and release: artifact suitability never authorizes those decisions by itself. Unknown proof-validation kinds fail closed.

DISPATCH and DELIVER use the separately qualified shipping/carrier lifecycle, not this photo validator. A retained shipping photograph does not prove a purchased policy or carrier event. The service must call validateEvidence before transitions and assertInTransaction again inside each transaction; upload authenticity and staff decisions remain separate from exact financial reconciliation and protection holds.

## Targeted evidence

The proof tests use actual Node 22 SQLite, actual encrypted disk objects and actual sharp decoding, with explicitly synthetic paid orders, actors, policy/reviewer authorities and physical dates. They cover original-byte recovery/restart and lost final commit, malformed and CRC-correct corrupt pixel streams, checksum/MIME/pixel/deadline refusals, encrypted-object tampering, wrong keys/symlinks/permissions, buyer/order/purpose privacy, staff review separation, service-guard rejection, cross-proof request reuse, runtime revocation during awaited decoding, asynchronous canonical-authority denial after decoding and before reviews/private responses, unchanged upload/return deadlines across refresh waits, actor-free readiness refusal and owned decoder shutdown. The joined service tests create actual synthetic-provider payments under the 8% fee and 24-hour terms, require reviewed packing, submit private buyer originals, preserve holds until separate return decisions and inspection, reconcile the original refund before closure, release only at the actual-delivery deadline, and keep non-return appeals compatible. These are synthetic business and carrier facts, not genuine financial or physical authority. No real customer upload, credentials, external provider request, label, shipping effect, shared database operation or production activation was performed. Historical PostgreSQL and payment qualification is reused within unchanged source bounds; it is not replaced by these tests.
